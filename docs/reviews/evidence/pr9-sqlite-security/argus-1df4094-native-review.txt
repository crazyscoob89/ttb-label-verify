### 3. Three defects to fix

**(a) BLOCKING — product bug: `[`/`]` in any path breaks the ledger.** Test #3 fails inside product code (`provision-demo.ts` → `assertPrivateLedgerCreation`), not the harness. Isolated repro (ACL set on ASCII name, then renamed so the descriptor is provably identical):

```
ascii / space / apostrophe / accent-é / Å / 日本  → ACCEPTED
ledger [literal]                                  → REJECTED  ← false positive
```

Cause: `Get-Acl -LiteralPath` in Windows PowerShell 5.1 still glob-expands `[...]` despite `-LiteralPath`. An operator with a bracketed data directory gets a permanently unprovisionable ledger with the opaque message `Private ledger security check failed`. Fix: use `[IO.DirectoryInfo]::new($p).GetAccessControl()` / `[IO.FileInfo]` instead of `Get-Acl`/`Get-Item`. (Note the Unicode part of that test name is a red herring — Unicode works fine.)

**(b) BLOCKING — the security tests are vacuous on a standard workstation.** `fixtureAcl(..., 'expose')` does `Get-Acl` → `AddAccessRule` → `Set-Acl`. `Get-Acl` returns a descriptor with a SACL section, so `Set-Acl` demands `SeSecurityPrivilege`, which non-elevated users lack:

> `The process does not possess the 'SeSecurityPrivilege' privilege which is required for this operation.`

So the two most important negative tests **error out instead of asserting**. Worse, this fails *open* as a red flag: the failure mode is indistinguishable from a real rejection to anyone skimming. Fix: build a fresh `DirectorySecurity` (no SACL) as the `private` branch already does — I confirmed that path needs no privilege.

**(c) Non-blocking — error messages.** Every failure collapses to one string with no reason code. Consider an internal discriminator (not surfaced to HTTP) so operators can distinguish "not NTFS" from "inherited ACL" from "stray ACE".
