7. OFFICIAL EVALUATION RUBRIC: WHAT A MODEL CAN AND CANNOT SATISFY
Correctness/completeness:
  Model evidence: seven-field, per-condition accuracy; warning checks; negative-field false matches; failures/referrals above.
  Remaining application proof: each image paired with its own declared application data, commodity-aware deterministic rules, explicit results for every field and no silent loss in a batch. No model currently receives an overall correctness PASS.
Code quality/organization:
  This is an application/repository criterion, not a model benchmark. Prior baseline review does not grade unbuilt UI/intake/orchestration. Verify separate intake, extraction, rules and UI responsibilities, tests and clear contracts for whichever provider is chosen. No extra model points for an unimplemented architecture.
Appropriate technical choices:
  Haiku offers the best observed false-match profile among the fast routes, but has external-route and Azure-availability uncertainty. Azure Mistral OCR offers strong extraction and zero processing failures in this suite, with substantial warning-format false matches. Grok is fast enough at median but markedly weaker in warning accuracy. All choices must justify cost, latency, dependency and manual-review trade-offs; no unnecessary microservices or multi-model ensemble without measured benefit.
UX/error handling:
  No model alone supplies a simple upload/result interface, intelligible mismatches, uncertainty display, retry controls or batch progress. Demonstrate clear per-item errors, side-by-side image/application/extracted values and a useful next action. Manual review is a cost and UX trade-off, not a magic accuracy repair.
Attention to requirements:
  Preserve all seven categories and applicability rules; relaxed brand normalization versus exact warning checks; batch mapping; complete deployed timing; source plus setup/run instructions and testable URL. Do not add COLA integration or claim universal TTB certification.
Creative problem-solving:
  Evidence-backed provider selection, explicit unsupported physical-size checks, deterministic rules around model extraction, and a bounded firewall-feasibility trial are defensible choices. They earn credibility only when implemented and demonstrated; extra complexity or more tests alone are not success.

8. PROPOSED FAILURE HANDLING (NOT YET A VERIFIED APP CAPABILITY)
• Validate input type/size and structured output. A malformed result, timeout or provider error produces a processing-error state with fields unresolved, never a green match.
• For transient service failures, proposed bounded retries must respect time and spend budgets. Do not silently exceed the five-second target through retry chains; show honest pending/failed status. Benchmark calls used no automatic retries.
• Readable disagreements are mismatches; missing/unclear readings are needs-review with a clearer-image/manual-review action.
• Exact deterministic checks cannot recover text/style that the model read incorrectly. Warning-format verification and physical type-size checks require explicit review until a separately validated detector/control exists.
• Show the evidence beside the proposed result and require human confirmation under the current prototype recommendation. This mitigates reliance; it does not establish corrected statistical accuracy or fulfill a stricter automatic-approval objective.
• Batch failures must not drop records or attach results to the wrong application. Bounded concurrency needs its own real-app latency/rate-limit test; sequential benchmark timings do not prove batch capacity.

9. RECOMMENDATION / NEXT ACCEPTANCE DECISION
Do NOT lock GPT-5 mini as primary given the speed requirement. Retain its benchmark as a quality reference, not a default fallback: a slow second call would worsen the latency target.

Keep TWO bounded candidates, with different purposes:
1) Haiku/OpenRouter: candidate if that provider route is acceptable for the demo; strongest observed false-match profile among fast options, not a verified Azure deployment solution.
2) Azure Mistral Document AI: candidate when Azure feasibility is essential; near-Haiku median and strong extraction, but explicit human warning verification remains necessary.
Grok stays a comparator rather than a third active build lane. Slower/less reliable tested configurations are parked. These conclusions apply to the exact tested routes/configurations, not every possible setting of a model family.

The next deciding evidence is the SAME minimal app flow measured on the shortlisted routes: upload → matched application record → seven-field output → displayed errors/review states. Record full latency distribution and usable-output rate, then exercise representative batch mapping and restricted-network routing in an isolated environment. Azure identity/resource binding may need resolving before network proof; no presumed access or customer certification.

Define the timing acceptance explicitly before that run: representative typical result within five seconds versus p95 within five seconds are different requirements. The app should report both regardless; do not call p50 alone a universal five-second guarantee. The assignment gives no numerical accuracy floor. Any new accuracy/automation threshold requires an explicit scoped decision, not an invented Treasury requirement.

Approval of a comparison report is not permission for new paid calls, infrastructure changes or an expanded build. Current next move is review this matrix and choose the bounded implementation/test scope.
